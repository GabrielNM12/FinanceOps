# FinanceOps

A self-hosted financial control system for a small Brazilian services company:
cash flow, tax provisioning, profit distribution between partners and savings
goals, in one ledger.

It was built to replace a spreadsheet and a group chat at a six-partner
software agency. Every month ended with the same questions: who paid what, how
much can actually be distributed, and how much of the bank balance already
belongs to the tax authority. FinanceOps answers all three.

> Português: [README.pt-BR.md](./README.pt-BR.md)

**Stack:** Next.js 14 (App Router) · TypeScript (strict) · Prisma · SQLite ·
Tailwind CSS · Recharts · Docker Compose · Caddy · GitHub Actions

**Highlights**

- Money is never a float: integer cents and basis points everywhere.
- Every transaction carries an accrual date and a cash date, so the dashboard
  switches between "what we earned" and "what we hold".
- A tax engine for Brazil's *Simples Nacional* that computes the effective rate
  from trailing 12-month revenue instead of a hard-coded percentage.
- Passwordless magic-link login with HMAC-signed sessions, re-authorized
  against the database on every request.
- Append-only audit trail, idempotent CSV imports, ID-preserving backup/restore.
- 245 assertions over the pure calculation core; every push to `main` is
  tested, built and deployed with a pre-deploy backup and automatic rollback.

## Quick start

Requires Node.js 18.18 or newer. One command from clone to running app:

```bash
git clone https://github.com/GabrielNM12/FinanceOps.git financeops && cd financeops
npm run tudo
```

`tudo` ("everything") runs `npm install`, prepares the database, builds and
starts in production mode. Open <http://localhost:3000>.

Running it again is safe: `db push` and the seed are idempotent, nothing is
deleted.

For development:

```bash
npm install
npm run dev
```

### Not in the repository

| File | Why it is excluded | How to get it back |
|---|---|---|
| `.env` | Will hold secrets such as `API_TOKEN` | Created automatically |
| `prisma/dev.db` | Real financial data | `npm run tudo` creates an empty one; restore a backup |
| `backups/` | Same | Must have been copied elsewhere beforehand |

The `.env` file is generated by npm `pre*` hooks before `setup`, `dev`,
`build`, `start` and every `db:*` command. The default value lives inside
`scripts/preparar-env.mjs` itself rather than in `.env.example`, because
generating a missing file from another file that might also be missing only
moves the problem. Without this, a fresh clone failed on its first command
with Prisma's unhelpful `P1012: Environment variable not found`.

**A fresh clone has no data.** Go to Import → Full backup and load the latest
`.json`.

### Language

The interface language is chosen per deploy, at **build** time, through
`NEXT_PUBLIC_APP_LOCALE`. Portuguese is the default; `NEXT_PUBLIC_APP_LOCALE="en"`
switches the UI, URL paths (`/impostos` → `/taxes`), access emails and number
format to English (currency stays BRL). Simples Nacional terms (DAS, Fator R,
RBT12, pró-labore, Annex III/V) are kept as-is in both languages.

## Glossary

The domain is Brazilian, so a few terms appear throughout the code and UI:

| Term | Meaning |
|---|---|
| Simples Nacional | Simplified tax regime for small companies; one monthly payment |
| DAS | The monthly Simples Nacional tax payment slip |
| RBT12 | Gross revenue over the trailing 12 months, which sets the tax bracket |
| Fator R | Payroll ÷ RBT12; decides which tax annex (rate table) applies |
| Pró-labore | Partners' salary; counts as payroll for Fator R |
| Competência / Caixa | Accrual basis / cash basis |
| Caixinhas | Savings envelopes ("little boxes"), as in Brazilian banking apps |
| NF | Service invoice (*nota fiscal*) |

## The decisions that matter

### Money is an integer number of cents

No monetary value is ever a `Float`. `0.1 + 0.2` is `0.30000000000000004` in
floating point, and in a financial report that becomes a few cents of
difference nobody can explain, which quietly destroys trust in the whole tool.
Percentages follow the same rule as basis points: `600` = 6.00%.

### Every transaction has two dates

`dataCompetencia` is when the fact happened (the service was invoiced).
`dataCaixa` is when the money moved; `null` means pending.

That is what powers the **Cash / Accrual** toggle on the dashboard and keeps
"invoiced" and "received" as different numbers. An invoice issued in January
and paid in March shows up in January on an accrual basis and in March on a
cash basis, as it should.

### Tax lives in two places and is never counted twice

When revenue is recorded, the DAS is **provisioned** in `fin_imposto`: it
reduces profit and free cash but is not yet a cash outflow. When the slip is
paid, an outflow is created in the ledger.

- On an **accrual** basis, tax comes from `fin_imposto` and tax-category
  outflows are excluded.
- On a **cash** basis, tax comes from paid slips and `fin_imposto` is ignored.

Every aggregate read goes through `src/lib/queries.ts`, so no screen builds its
own aggregation and ends up double-counting.

### Free cash

```
free cash = bank balance − tax provisioned on revenue ALREADY RECEIVED
```

This is the most useful number in the system. The account may hold R$ 80k, but
if R$ 9k of it is tax on money that came in, what can be distributed is R$ 71k.

Money in savings envelopes is not part of this number because it has already
left the checking account; subtracting it again would count it twice.

**Tax on unpaid invoices is excluded.** An invoice that has not been paid has
not put money in the account, so its tax cannot take any out. When the client
pays, both arrive together.

The trade-off is worth knowing: **the DAS is due on invoicing, not on
receipt.** If a client pays late, the slip is still due and becomes an outflow
free cash did not anticipate. That amount therefore stays visible in three
places (the receivables card, the payables total and a dedicated dashboard
alert), and the Taxes screen marks each slip as *received* or *receivable*.

The rule lives in `src/lib/caixa.ts`, pure and covered by tests, so there is
only one definition in the code.

### Savings envelopes

Separate pockets, like the ones in Brazilian banking apps. Saving **moves money
out of the account** into the envelope; withdrawing moves it back. Each envelope
has a name, color, icon and an optional goal with a progress bar.

| Number | What it is |
|---|---|
| **In account** | Checking-account money, net of what is saved |
| **Saved** | Sum of all envelopes |
| **Net worth** | Account + envelopes; does not change when you save |

Saving does **not** affect the month's profit: it is neither revenue nor
expense, just a transfer between your own pockets.

Each movement writes two records in the same database transaction: the envelope
movement (the source of truth for its balance) and a transfer in the ledger, so
the in-app statement stays complete and reconcilable with the bank's. If one
fails, neither is written.

**An envelope's balance is never stored**; it is always the sum of its
movements. A stored total that drifts out of sync lies forever and nobody
notices.

The system enforces the obvious rules: you cannot save more than the account
holds or withdraw more than the envelope has; an envelope with a balance cannot
be archived, and one with history cannot be deleted, because deleting it would
retroactively change the account balance.

A **capital contribution** is different: new money from a partner raises net
worth but is neither revenue nor taxable.

### The tax rate is computed, not typed in

Under Simples Nacional the effective rate depends on RBT12, and the app already
has that history:

```
effective = (RBT12 × nominal − deduction) ÷ RBT12
```

The annex comes from **Fator R** (`payroll ÷ RBT12`): 28% or more leads to
Annex III, starting at 6.00%; below that it is Annex V, starting at 15.50%.
Pró-labore counts as payroll; profit distribution does not. The dashboard shows
the current Fator R and the gap to 28%, but decides nothing; that conversation
belongs with the accountant.

Brackets live in the **`fin_faixa_simples` table**, not in code. Tax law
changes, and recompiling the app for it would be a mistake. The rate used is
stored on each provision, so editing a bracket later never rewrites history.

### Distribution, pró-labore and reimbursement are different things

| Type | Is it an expense? | Counts toward Fator R? |
|---|---|---|
| `LUCRO` (profit) | No, it is an allocation of profit | No |
| `PRO_LABORE` | Yes | **Yes** |
| `REEMBOLSO` (reimbursement) | No, the expense was already recorded | No |

Treating all three as plain outflows would inflate expenses and hide Fator R.

### Recurring expenses are materialized

When a recurring expense comes due, a real entry is created (pending payment)
instead of being computed on the fly. That lets you edit that month's amount
(the electricity bill is never the same twice) and keeps history matching the
bank statement. Idempotency comes from a unique `(recorrenteId,
competenciaRef)`: running the generation 50 times produces the same entries.

The **future** remains pure calculation. Materializing it would create expenses
that do not exist yet and pollute every accrual report.

### Imports never duplicate

Each CSV row becomes a SHA-256 of `date + amount + normalized description`,
stored in a `unique` column. Re-importing a whole month's statement skips what
already exists. Imports are always two-step (preview, then confirm), because a
wrong CSV pollutes months of history and there is no cheap undo.

### Restoring a backup

Import → **Full backup** takes the `.json` in two steps, like CSV. The preview
shows, table by table, what exists now and what the file contains.

- **Replace everything** wipes current data and recreates the database from the
  file. IDs are preserved, so the result is identical to the original, not
  merely similar. Requires explicit confirmation when data already exists.
- **Merge** inserts only what does not exist yet, by ID. Nothing is
  overwritten.

Everything runs in a single transaction: if one row fails, nothing is written.
Before writing, every foreign key in the file is checked against records
present in it.

### Audit trail: who did what

Two different things, on purpose:

| Where | Answers | Cost |
|---|---|---|
| `fin_transacao.criadoPorId` | "Who entered this?" | On the row, no join |
| `fin_auditoria` | "What happened in the system?" | One row per event |

Neither replaces the other. A field on the ledger alone would lose
**deletions**, since the record disappears and takes its author with it. The
trail alone would force a join per row just to show authors in a list.

The trail records what does not become a ledger entry: tax slips paid or
reversed, CSV imports, backup restores, access-email changes, deletions.

**It is append-only.** The application never edits or deletes it; a record the
system itself can alter cannot audit the system. `registrar()` **never throws**:
if auditing fails, the operation has already happened, and failing the request
would make the user believe nothing was saved.

Entries created before the audit trail existed were attributed in bulk by
`scripts/retroagir-autoria.mjs`, and that bulk attribution is itself recorded
in the trail. An audit log that hides how its data got there gives confidence
without basis.

## Frontend performance

**Navigation is instant.** Clicking a sidebar item never waits for the server:

1. **`loading.tsx` in every route** makes the URL change on click. Without it,
   Next.js keeps the old screen until the new route's JavaScript downloads.
   With the Suspense boundary, the skeleton renders as static HTML right away.
2. **The component mounts** and shows the same skeleton while it fetches JSON.
   The handover is invisible by design.
3. **The data arrives** and fills the content; title, filters and layout were
   already in place.

Skeletons match the real content's dimensions exactly, because a placeholder
of a different size makes the page jump, and the jump is more annoying than the
wait. After an action, refetches are **silent**: a thin bar appears at the top
and the old data stays on screen until the new data arrives.

Every screen is static at build time. The dashboard used to be the exception
because it shipped Recharts with it; charts now load through `next/dynamic` in
a separate chunk, so KPIs appear without waiting for the charting library:

| Route | Before | After |
|---|---|---|
| `/` (dashboard) | 217 kB | **107 kB** |
| other screens | 94–106 kB | 94–106 kB |

On mobile, tables in Transactions, Taxes and Recurring turn into cards below
the `md` breakpoint (eight columns do not fit in 360 px, and horizontal
scrolling in a financial list hides the amount column), and KPIs collapse to
two columns.

### Two APIs, on purpose

| Route | Audience | Contract |
|---|---|---|
| `/api/ui/*` | This app's screens only | Changes with the layout, no notice |
| `/api/v1/*` | Integrations | Stable; see `INTEGRACAO.md` |

If the UI consumed `/api/v1`, any screen tweak would silently break whatever
system reads the data.

**Writes stay in Server Actions.** Only reads moved to `fetch`. Actions already
validate, run in transactions and know the domain rules; turning them into
POST endpoints just to "be a SPA" would duplicate that logic on the client,
which is exactly where validation gets lost.

## Authentication

Login is by **magic link**: enter your email, click the button you receive,
you are in. There is no password to leak, reuse or forget.

Deliberately small, one table and one cookie:

| Piece | What it does |
|---|---|
| `fin_token_acesso` | Link token, stored **hashed**, single use, 15 minutes |
| Signed cookie | HMAC-SHA256 over `{email, exp}`; no session table |
| `src/lib/acesso.ts` | Who may sign in; pure and tested |

There is no user table and no session table. Identity is the partner's email,
and the session is a cookie carrying its own signed content. Revocation is not
weakened: `sessaoAtual()` checks **on every request** that the email still
belongs to an active partner, so deactivating someone cuts access immediately.

Signing uses **Web Crypto**, not `node:crypto`, so the same code validates the
cookie in the middleware (Edge runtime) and on the server.

| Layer | Question | Runtime |
|---|---|---|
| `middleware.ts` | "Is the cookie signature valid?" Redirects to `/login` | Edge |
| `exigirSocio()` | "Does this email still belong to an active partner?" | Node, with database |
| `exigirAcesso()` | Same question, in every server action that writes | Node, with database |

**The middleware is not a security boundary**: it never touches the database.
The check that counts is repeated on the server. Server actions get their own
guard because they are ordinary POST endpoints; anyone who knows an action's ID
can call it without going through a screen.

The login screen gives **the same answer** for authorized and unknown emails,
so it cannot be used to discover who has access. When a session expires with a
screen open, the client redirects to login and preserves the return path in
`?destino=`.

### Configuration

```bash
AUTH_SECRET="..."              # openssl rand -base64 32
SMTP_HOST="smtp.example.com"
SMTP_PORT="587"
SMTP_USER="financeops@example.com"
SMTP_PASS="app-password"       # not the account password
EMAIL_FROM="FinanceOps <financeops@example.com>"
```

Without SMTP, in development the link is printed to the **console**, so the
whole flow can be tested without credentials. In production login refuses to
work, so nobody believes an email was sent when it was not.

For a first sign-in on an empty database, `AUTH_BOOTSTRAP_EMAIL` lets one
address in without belonging to any partner. **Remove it afterwards.**

`npm run auth:diagnostico` explains why an email did not arrive (unknown
address, inactive partner, SMTP not loaded by the running process, or SMTP
rejection), since by design the login screen cannot tell them apart.

## Deployment

```
internet → Caddy (80/443, automatic HTTPS) → financeops:3000 (internal network)
                                                    ↓
                                          volume financeops-dados
                                          /dados/financeops.db
                                          /dados/backups/
```

The app **publishes no port on the host**: only Caddy talks to the internet and
terminates TLS. That matters because the emailed access link is a credential;
over plain HTTP anyone on the network path could read it and sign in.

Every push to `main` runs tests, type checking and a build on GitHub; if they
pass, a runner on the server backs up the database, pulls, rebuilds, restarts
and checks health, and **rolls back to the previous commit automatically** if
the health check fails. See [`CI.md`](./CI.md) and [`DEPLOY.md`](./DEPLOY.md).

A separate demo instance with fictional data and login disabled is described in
[`DEMO.md`](./DEMO.md).

## What this system is not

- **Not accounting software.** It does not produce official statements, file
  taxes or issue payment slips. Its numbers are estimates for decision-making;
  official figures come from the accountant.
- **It does not compute payroll charges** on pró-labore (INSS, IRRF). Record the
  gross amount and the charges as a separate expense.
- **The source of truth is still human.** If nobody records anything, the system
  lies with confidence. That is why CSV import is the most valuable feature on
  the list, more than the charts.
- **Access is email-only.** Whoever controls a partner's inbox controls their
  access, so turn on 2FA for those email accounts.

## Project structure

```
prisma/
  schema.prisma        # data model; every table prefixed with fin_
  seed.ts              # Simples brackets, categories, partners
src/
  lib/
    money.ts           # cents, basis points, splitting without losing a cent
    datas.ts           # accrual periods and windows, anchored in UTC
    simples-calc.ts    # pure Simples Nacional arithmetic (what the tests cover)
    simples.ts         # shell that loads data and calls simples-calc
    queries.ts         # EVERY aggregate read for the dashboard
    recorrentes.ts     # idempotent materialization + projection
    caixa.ts           # free cash, balances, envelope goals (pure, tested)
    csv.ts             # parser, dedupe hash, export
    acesso.ts          # who may sign in (pure, tested)
    db.ts              # Prisma singleton
  actions/             # server actions (writes)
  app/                 # routes: dashboard, transactions, taxes, envelopes,
                       # recurring, import, audit, settings, api/v1, api/export
  components/
    graficos.tsx       # Recharts; draws, never calculates
```

The golden rule: **aggregate reads go in `queries.ts`, arithmetic goes in
`simples-calc.ts` or `money.ts`.** Components never calculate; they only draw
what the data layer already computed. That is what keeps the screen and the
report from disagreeing.

Integration with other systems (dialect-agnostic DDL, type mapping, API routes
and a migration path to PostgreSQL, MySQL or SQL Server) is documented in
[`INTEGRACAO.md`](./INTEGRACAO.md).
